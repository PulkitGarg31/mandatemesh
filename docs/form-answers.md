# Google Form answers (draft; paste into the one-shot form)

**Project Name / Title**
MandateMesh: a mandate-scoped buyer agent with a deterministic policy gate on Razorpay

**Project Objectives (What does it solve?)**
Agents are about to spend money on people's behalf, and the open question in every protocol effort (NPCI's UAP, Google's AP2, OpenAI/Stripe's ACP) is the same: how do you stop a machine from going rogue? MandateMesh answers it in miniature on Razorpay test mode, and makes three claims. **One: a mandate can only shrink when it is delegated.** An agent may hand its authority to another agent by signing a sub-mandate, and the gate verifies every link of that chain — signed by the delegator the previous link named, and narrower in currency, both caps, merchants, categories and expiry (rules R18 and R19). Spending caps are enforced against every link at once, so delegation can never multiply the budget. **Two: every money action is gated, including the refund.** A merchant can attest that a paid-for line was not delivered, but only the gate authorizes money back, priced from the signed cart rather than from the merchant's claim, capped by what was captured minus what was already refunded, and refusing a duplicate attestation (rules RF00–RF08). **Three: the audit trail replays offline.** `ledger replay` re-decides every purchase and refund from the ledger file alone and compares the result to what was recorded, so a doctored verdict is caught even when the hash chain was recomputed to fit; `verify` is record integrity, `replay` is reasoning integrity. Underneath, the Part I design still holds: a user signs a spending mandate (total cap, per-transaction cap, merchant allow-list, categories, expiry); an untrusted LLM agent browses an agent-readable catalog and proposes a cart; a deterministic, non-LLM policy gate verifies an Ed25519-signed intent → sub-mandate → proposal → cart → payment chain against 20 ordered rules (plus a guard that turns any internal error into a deny) and is the only component that can create a Razorpay Payment Link; the executor holds the Razorpay keys and the LLM never sees key material; every step lands in a hash-chained audit ledger with an exportable receipt. Failures are handled gracefully: cap exceeded → user-signed step-up bound to that exact cart; payment failed → recorded, one gate-authorized retry, then honest abandon with the link cancelled; poisoned catalog text → bounded by the gate; revoked agent → denied; a delegator granting more than it holds → denied with nothing created; an inflated refund claim → denied; Razorpay errors → recorded and the link closed. Result: every money action is explainable (rule-by-rule trail, mandate ids on the Razorpay object), bounded (pure-function policy, not a prompt) and gated (the model never touches keys or Razorpay). An offline eval of 17 hand-built cases blocks 11/11 abusive proposals with 0/6 false positives across eleven distinct rules, and 193 offline tests run without network.

**Build Challenges & Technical Obstacles**
- The form is a one-shot final submission requiring the repo and video, so the two-week research plan was cut to about 16 hours: one merchant, no UI, no webhooks, polling instead. I kept the parts the track bar rewards (gate, mandate chain, ledger, failure paths) and cut the rest.
- No paid LLM credits: the agent talks to any OpenAI-compatible endpoint, so Gemini's free tier, a local Ollama model and Groq all work through one code path. The installed `openai` client was 3.7, not the 1.x the plan assumed: tool calls are a union type that has to be filtered to function calls, Ollama rejects `tool_choice` so none is sent, and Gemini 3 returns thought signatures that must be echoed back or the next turn fails. Groq also retired the model the plan named, so the example config moved to `openai/gpt-oss-120b`. That turned into a design point: the trust layer must not depend on which model proposes.
- Razorpay test mode allows only 30 Payment Links, so I built a fake executor with the same interface for all tests and development and rationed real calls to the smoke test and the recorded runs.
- Detecting a failed UPI attempt without webhooks: Razorpay's Payment Link `payments` array lists only captured payments, which I caught in review before any real call. The executor now reads attempts from the link's order (`GET /orders/{id}/payments`), with the Payments list matched on the mandate id in the link's notes as the fallback, verified by network-free regression tests and a one-time smoke script.
- Code review kept finding fail-open edges and each one became a rule or a guard: the signature originally covered only the payload (now binds signer and algorithm); dataclasses do not type-check, so a string amount crashed the gate (now strict parsing and rule R00); a 10^400 cart total crashed the money formatter (now integer money and an R99 guard so the gate never raises); a colluding merchant could sign a negative-quantity line (R10 hardened); the ledger receipt matched ids by substring; the orchestrator could record a link as cancelled when the customer had just paid (now a final poll and an honest `cancel_failed`); and Rich swallowed `[gate]` prefixes as markup.
- Delegation review found the same class of gap twice. When the subset rule (R19) denied, the chain-shape work had already been done but no R18 result was recorded, so the trail showed a subset failure with no evidence the chain itself was sound; the walk is now two passes and R18 is recorded first. The same pass added two missing refusals: a repeated `sub_id`, which makes one grant look like a chain of fresh authority, and an over-long chain, now capped at 8 links. Cap breaches under delegation were also reported against the leaf agent, which read as if only the junior agent had over-reached; the detail now names the root-most breaching link.
- Refunds needed the real API shape before rules could be written around it, so `client.payment.refund` was exercised once in test mode: the refund came back with status `pending` rather than `processed`, so the executor records whatever status Razorpay returns instead of asserting one. The design question that took longer was who names the amount — trusting the merchant's number would make the merchant the authority on how much of the user's money comes back, so the gate reprices the refund from the signed cart and refuses any claim that does not match it exactly.
- Making the ledger replayable was mostly discovering what a decision event does not say: the proposal is reachable only through the cart's `proposal_id`; `chain_ids[0]` is the root intent rather than a sub-mandate; public keys ride on events that are about something else; the live registry makes revocation permanent, so a naive rebuild is more permissive than the registry it imitates; the decision payload mixes the verdict with bookkeeping, so only the four decision fields can be compared; and the gate must not import the ledger, which makes the import inside `replay()` load-bearing rather than cosmetic. Replay is also deliberately total — a missing input is reported as an unreplayable decision, never an exception and never a silent pass.
- Carried over from the first half and still shaping this one: Razorpay's Payment Link `payments` array is captured-only, the free NVIDIA NIM endpoint 404s or 410s on most listed models so one working model is pinned rather than a menu, and small local models (llama3.2, mistral on CPU) fail closed with empty or invented carts — the design working as intended, but not a demo.
